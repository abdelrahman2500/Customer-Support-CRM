## Dependency notes

- Extends the existing `TicketsModule` (`tickets.controller.ts`, `tickets.service.ts`, `tickets.events.ts`) — no new module, no new controller file.
- **Adds exactly one new Prisma model, `TicketNote`**, in the already-declared `ticketing` schema, structurally mirroring `TicketHistoryEntry` (ticket-scoped, cascade-deleted, single `@@index([ticketId])`, no own `branchId`) — with one deliberate, disclosed deviation: `authorUserId` is **required**, not nullable, because unlike a history entry (which can be system-generated, e.g. an SLA escalation with no human actor), a note can only ever be created by a deliberate, authenticated agent action.
- **No new permission key.** Note creation reuses `ticket:create` (mirroring the exact precedent of `POST /customers/:id/contacts` reusing `customer:create` rather than minting a `contact:create` key); note reading reuses `ticket:read` (mirroring `GET /tickets/:id/history`'s exact reuse of `ticket:read`). `ticket:update` is never invoked — notes are append-only, there is no edit/delete route.
- **This story is deliberately, explicitly NOT the seed of the future Communication/Channels domain.** `docs/architecture/03-domain-boundaries.md` assigns "inbound/outbound messages, threads" to the `channels` schema, never `ticketing` — and `docs/architecture/06-communication-and-realtime.md`'s entire `ChannelMessage` vocabulary (channel type, external thread id, sender, provider) describes only externally-sourced, customer-facing conversation. `TicketNote` introduces **no** `channel`/`source`/`externalRef`/discriminator field of any kind, is never customer-visible, and is not designed to be unified with the eventual `ChannelMessage` model — that remains an entirely independent, future, dedicated planning decision for the Channels domain, not preempted here.
- Realtime: a new `ticket.note-added` domain event, relayed into the **already-existing** `ticket:{id}` room by one new `@OnEvent` handler added to the already-existing `TicketRealtimeListener` — no new gateway, no new room, no new socket-authentication path. Its payload shape (`{ ticketId, note }`) deliberately differs from the other four ticket events' shared `{ ticket, actorUserId }` shape, since `useTicketRealtime`'s handler ignores payload contents entirely today (blanket invalidation on any subscribed event) — a disclosed, inconsequential shape difference, not an oversight.
- Frontend: extends `tickets-api.ts`/`use-tickets.ts` in place (no new dedicated file — this is a ticket-scoped concern, exactly like the existing history/SLA-target/escalations reads), and adds one new card to the existing Ticket Detail screen, appended after the History card (the established append point: SLA → Escalations → History → Notes), mirroring the History/Escalations cards' exact loading/error/empty/populated JSX shape plus a small inline add-note form mirroring `AddDepartmentForm`'s established "smallest UI surface for a one-field create" convention.
